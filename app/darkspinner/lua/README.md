Build with `mage scenario:build`, then run `bin/game/darkspinner.exe --lua local/two_arsenal.lua`. Development launchers read `app/darkspinner/lua` directly from the repository on disk; standalone scenario launchers read `<darkspinner-directory>/darkspin/lua`. Each run reopens the selected source file. Lua sources are not embedded, copied, migrated or retained by hash. The source folder includes LuaLS definitions and `.luarc.json` for Lua 5.1. Ordinary builds exclude the scripting VM, private control bridge and scenario input code, and reject the debug flags.

Use `mage darkspinner:buildrunlua two_arsenal` to build the scenario launcher and run a script by shorthand. The `.lua` suffix is optional. Resolution checks the Lua root first, then searches subdirectories for a unique filename; use `local/two_arsenal.lua` to specify a path explicitly. The command resolves the same repository source directory as the development launcher; old runtime copies cannot shadow edited sources. Missing and ambiguous names fail before building, with ambiguous paths listed for selection. Explicit diagnostic captures retain the exact source bytes used for that run; their hashes record provenance only. The command opens the launcher, selects its development Lua tab, and automatically runs the chosen script. The tab has a searchable list of unique scenario names without `.lua`, footer Run, Stop session and Kill all controls, activity without per-line timestamps, elapsed completion status, failure traces, and a bottom copy icon for agent handoff. The script inventory is read at launcher startup and refreshed before each run. Duplicate basenames report their conflicting paths. Console output stays in a bounded in-memory buffer rather than a separate file for each session. A fresh launcher clears old detached launch/trace logs, client-result mailboxes, and obsolete launcher console logs. Only clients launched by the current launcher are tracked; previous processes remain untracked after restart. Native registration/failure files are a temporary handoff and are deleted after their contents reach launcher memory; Send report includes the retained in-memory results.

For agents, `bin/game/darkspinner.exe --lua-headless local/two_arsenal.lua` starts only the supervisor and Lua helper, with no launcher UI. `--debug-api --lua <path>` also remains supported. Read the printed private discovery file and use its authenticated `POST /dev/scenario/v1/scripts/run` with `{"path":"local/two_arsenal.lua"}` to run another script in the same session. A running script rejects concurrent runs. Completion retains the server and clients for inspection (up to the existing 30-minute retention). Stop session calls authenticated `POST /dev/scenario/v1/scripts/stop` to cancel only the running Lua script; the supervisor, clients and server remain available, and another script can reuse them. Kill all terminates the owned clients and server. `POST /shutdown` and closing the launcher still perform full session cleanup. Compatible `scenario.StartServer({})` calls reuse that session's server. Changed server inputs require Kill all or full session shutdown first. The authenticated `POST /dev/scenario/v1/kill` force-closes session-owned clients and stops its server; it also cancels an in-progress graceful shutdown. Content snapshots use read-only SQLite online backup when the source is open or has WAL sidecars, then preserve an exact offline copy without checkpointing the source. An unrelated launcher/server is not automatically adopted or terminated.

Each script returns its entry function. The helper loads the source first, then calls that function; operations cannot run during top-level source evaluation. Server, profile and client objects retain their scope. Editor definitions are split across `definitions/` by server, profile, client, scene, UI, window, session and error scope; `scenario.lua` contains root helpers and compatibility functions.

```lua
local must = scenario.Must

return function()
    local server = must(scenario.StartServer({}))
    local profile = must(server:CreateProfile({
        name = "normal",
        hero_nouns = {1667741389, 3618328019, 749013658},
        chain_progression = 1,
    }))
    local client = must(profile:Launch({client_id = "normal", launch_mode = "normal"}))
    must(client:Login())
    must(client.Scene:Wait(scene.Arsenal))
    must(client.UI:Screenshot("arsenal"))
end
```

Fallible methods return `result, err`, or only `err` for operations such as `Close`. Use `scenario.Must(result, err)` for a required result and `scenario.Check(err)` for an error-only operation. Local aliases `must` and `check` avoid repeating the namespace. There is no manual context-label argument: structured errors already preserve operation breadcrumbs, and raised errors capture the Lua call-site traceback. `Must` raises on either a non-nil error or a nil result; false is valid. Optional results need explicit nil handling after `Check(err)`. The LuaLS nonnullable return type reflects this runtime check. The older global `run()` entry remains accepted for developer-owned scripts, but shipped scripts use returned functions and no lowercase global declarations.

`UI:Type(text)` sends one bounded batch of 1–256 printable ASCII characters through the owned window's existing handler. It does not change desktop focus or the clipboard, select a text field, or submit Enter. A processing receipt reports `processed_character_count`; it does not prove text acceptance or chat delivery. Partial processing retains its count and an error, and is never replayed. `UI:Click(x, y, "right")` opens ordinary native context menus with paired right-button input; omitted button defaults to left.

`UI:Hierarchy()` / REST operation `client.ui_hierarchy` saves an `editor-ui-*.json` artifact beneath this client's scenario log directory and returns its path, SHA-256 and nodes. A launched client defaults to a 60000-millisecond timeout. Set `timeout_ms` in `profile:Launch({...})` to choose another default, or call `scenario.Check(client:SetTimeout(45000))` later. `Login()`, `Ready()`, `Scene:Wait()`, `Scene:Set()` and `Mission:Wait()` use the current client default when their timeout is omitted; an explicit per-call timeout overrides only that call. Existing scoped objects inherit timeout changes dynamically. Timeout settings are milliseconds from 1 to 120000. `Login()` blocks for accepted live server authentication and returns `LoginObservation, err`; it does not imply native UI or world readiness.

`scenario.Time()` returns monotonic elapsed milliseconds since script execution began. Save `local started = scenario.Time()` and later compute `local elapsed = scenario.Time() - started` to measure a step. `normal:Time()` reports elapsed milliseconds since that client's launch began, including launch duration; subtract two snapshots from the same clock to measure an interval. Both return a number directly, permit fractional milliseconds, and have no error slot. Saved wall-clock timestamps remain unchanged.

Scenario launches default both `is_intro_skipped` and `is_cinematic_skipped` to true; pass false separately to retain introductory movies or in-game cinematics. The ordinary launcher defaults both to false. Live changes remain independent: `scenario.Check(client.Cinematic:SetSkipEnabled(false))` retains in-game cinematics, while `scenario.Check(client.Cinematic:SetIntroSkipEnabled(false))` retains introductory movies. Changing one switch leaves the other unchanged.

`local/two_profiles.lua` creates two isolated profiles and launches normal and detached clients. `local/seed_reset.lua` demonstrates distinct squad orders and a fresh reset before launch, verifies that reset allocated another account, and checks each accepted Arsenal login against its intended profile identity. `local/two_arsenal.lua` creates a normal seed, clones its selected squad/progression into the detached profile, and waits for Arsenal report plus owner-thread responsiveness before saving screenshots. `local/two_arsenal_parallel.lua` logs in both clients sequentially, then runs their scene waits and screenshots as named concurrent branches with a shared completion barrier.

Creating an existing profile alias, or resetting one explicitly, closes its session-owned clients and releases their launch names before creating a fresh account. Closure is attempted gracefully with bounded termination fallback for owned processes. The alias changes only after account creation and credential issuance succeed; the previous account and primary saves are unchanged. The replacement may reuse the client ID, with fresh private launch directories. Source cloning reads accounts already in the isolated server; importing a primary-save profile is unavailable.

`client:Close()` requests the ordinary window close and waits for exit; the native game may present its Quit confirmation and leave the operation waiting. `client:Terminate()` explicitly stops only that session-owned client and its detached helper, waits for exit, and returns an error-only result for `scenario.Check`. It does not confirm game save/quit dialogs. The REST equivalent already exists as `client.close` with `is_terminate=true`; `Close()` keeps its graceful behavior.

`local/repeat_mission.lua` runs two complete seeded normal/detached party mission entries on one owned server. The second detached seed clones the newly reset normal profile. `client.UI:InspectWindow()` makes an authenticated round trip through Fang and returns copied owned-window metadata, including its native owner thread and dimensions. `client.UI:Click(x, y)` queues a finite left click through that window's existing handler on the owner thread. Coordinates are client coordinates from `InspectWindow()`. Processing receipts prove neither enabled in-game controls nor gameplay success. The adapter sends no desktop cursor/focus commands. Requests have bounded deadlines and are never automatically replayed; timeout/disconnect may leave an unknown outcome, so inspect state before another action. The older `Window()` name remains a deprecated compatibility alias.

`client.UI:Screenshot(label)` saves the exact owned window and metadata under game logs, including for a background window. It returns `artifact, err`; unavailable capture can still return diagnostic metadata with the error. Required screenshots can use `must(client.UI:Screenshot("ready"))`. Authentication, capture success and gameplay readiness are independent observations.

`client.Diagnostics:Capture("failure")` returns `DiagnosticCapture, err` and uses the same operation as REST `client.capture` with `{client_id, label}`. It saves a manifest under the owned client's logs, a screenshot through the existing capture path, the client snapshot, allowlisted server profile/mission state, a fresh Fang window receipt, and copies of the last complete records from the client trace, server protocol trace and server log. Each log copy is capped at 512 KiB and records its sampled source size, offset, truncation and SHA256; it is a saved tail rather than a complete packet archive. Labels follow screenshot naming rules. Calls inherit the client timeout with a ten-second cap; at most 32 captures are reserved per supervisor, including partial attempts. Existing screenshot budgets also apply.

Captures are sequential observations with `is_atomic=false`; they do not pause the game or prove native world readiness. Every failed component appears in the manifest's lowercase `failures` snapshots, `is_complete` becomes false, and the call returns an error with typed `Failures`; successful components remain on disk. A stopped client can still yield retained trace tails and a partial manifest, but no newly reset alias's profile is attributed to it. Inspect the partial result before calling `check(err)` when evidence matters. Endpoint capture is observational and remains available during a running script. Pause automation until settled before inspecting the same client's native bridge to avoid competing with its one pending command. `two_clients.lua` captures both participants at final shared entry.

`client.Scene:Snapshot()` exposes accepted live authentication, current server game/party membership, retained client presence and mission lifecycle metadata through an explicit allowlist. These sources are independently sampled. `client.Scene:Wait(scene.Arsenal)` waits for authenticated matching reported presence and a pure native `scene.ready` query on the owner thread: the expected current room, loaded/enabled UI, eligible progression/mode and no active camera/movie must all match. It then rechecks report, authentication and client identity within one deadline. Explicitly unavailable eligibility probes may be retried within that deadline; this wait sends no transition or input. The result contains `client_id`, `instance_id`, `pid`, `state` and `readiness`; partial evidence may accompany an error. `client:Ready()` returns the same evidence shape with a window responsiveness probe only, without scene-specific eligibility. Neither guarantees final rendering or gameplay readiness.

Scene constants are `scene.Arsenal`, `scene.Navigation` and `scene.Editor`. Scene waits require a presence revision strictly greater than `afterRevision` (default 0). Default 0 accepts an existing retained report; capture a baseline revision first when a later changed envelope is required. Presence itself is a last client report and becomes stale after authentication ends. `Profile:WaitForReportedLocation` and compatibility location methods retain their report-only behavior; use `Client.Scene:Wait` for the additional native current-room and UI-eligibility checks.

Top-level overlays use `client.UI.Screen`, separately from the ship room. Supported constants are `screen.Profile`, `screen.Inventory`, `screen.Galaxy`, `screen.Friends`, `screen.Leaderboards`, `screen.Manual` and `screen.None`. `Set(target)` dispatches one ordinary native action and waits for observed selection; `Wait(target)` only observes, `Snapshot()` reads once, and `Close()` sets `screen.None`. All use the client timeout unless overridden. Selecting an already selected screen returns without another toggle. Close Inventory explicitly before selecting another overlay; native close gates and prompts remain intact. An unknown active modal/overlay is reported as unsupported and cannot be silently dismissed.

must(client.UI.Screen:Set(screen.Inventory))
must(client.UI.Screen:Close())

Browser screens are observed through the displayed frame and selected DOM tab; the client's cached `native_screen_id` can remain `-1`, while `selection_source="dom"` identifies actual selection. `is_content_ready` remains unknown: selection does not prove network content, animations or rendering finished. `local/screen_flow.lua` adds 1500 ms before diagnostic captures, visits all six overlays, checks Inventory transition refusal, and opens Profile from Navigation before returning to Arsenal. The real flow passed in 38 seconds with eight complete capture bundles and inspected screenshots (`bin/game/logs/scenarios/screen-flow-dom-oct24/analysis.json`).
