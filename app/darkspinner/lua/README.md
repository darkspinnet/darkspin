# Darkspinner development scripts

For a web launcher without an automatic browser window, use `bin/game/darkspinner.exe --headless --no-browser` and open its printed local URL in the desired browser. The web listener and manual tray action remain available.

`local/missile_barrage_render.lua` enters mission 1-4 with SRS-42, creates a stationary gunner, and casts Rocket Barrage once through `client.Ability:Cast(targetPosition, 60000)`. A parallel recording branch takes screenshots during the cast. It verifies the matching server cast's acceptance, every missile launch, release, and burst completion; no manual ability input or Power-loss inference is required. Review the saved screenshots for the terrain-disappearance symptom. Successful cast completion does not prove that terrain rendered correctly.

Camera investigations are `local/camera_ability_cancel.lua` (mission 3-4, Ride the Lightning followed by native cancellation and walking) and `local/camera_held.lua` (mission 6-4, alternating 600/1200 ms held movement and a hero switch). Run either with `--lua-headless` and `--lua-timeout 4m`. Both capture native camera observations and stop on unknown input outcomes without replaying them. The held scenario uses fixed aim and releases between trials; it does not cover uninterrupted long holds or cursor steering. `scenario_move_hold_active` records the client's actual continuous-movement state. `Ability:Cancel()` invokes the native cancellation producer; its receipt proves local dispatch only, so verify ActionCancel in the captured RakNet traffic. Camera mismatch thresholds identify candidates for review, not a proven gameplay defect.

PvP starters are `local/pvp_1v1.lua` and `local/pvp_2v2.lua` (allow a longer script timeout, such as `--lua-timeout 5m`, when launching four clients). Create participants with `is_pvp_enabled=true`; this seeds a separate valid PvP deck and preserves the campaign squad. `server:StartPVP({teams={{firstClient},{secondClient}}})` forms 1v1, while `teams={{firstClient,secondClient},{thirdClient,fourthClient}}` forms 2v2. Every participant must be a distinct live authenticated owned client outside an existing game or party. This is an explicit server fixture using production arena formation and setup notifications, not a test of the native matchmaking queue. The returned receipt reports game/team identities, formation acceptance and notification delivery; it does not claim native acceptance or loading. Call every participant's `PVP:Accept()` concurrently through `scenario.Parallel`, then `PVP:Wait()` for accepted PvP decks, the actual server opening countdown/combat transition and native world readiness. `PVP:Snapshot()` only samples the native arena lobby. Unknown or partially delivered actions are not automatically replayed.

Build with `mage scenario:build`, then run `bin/game/darkspinner.exe --lua local/two_arsenal.lua`. Development launchers read `app/darkspinner/lua` directly from the repository on disk; standalone scenario launchers read `<darkspinner-directory>/darkspin/lua`. Each run reopens the selected source file. Lua sources are not embedded, copied, migrated or retained by hash. The source folder includes LuaLS definitions and `.luarc.json` for Lua 5.1. Ordinary builds exclude the scripting VM, private control bridge and scenario input code, and reject the debug flags.

Use `mage darkspinner:buildrunlua two_arsenal` to build the scenario launcher and run a script by shorthand. The `.lua` suffix is optional. Resolution checks the Lua root first, then searches subdirectories for a unique filename; use `local/two_arsenal.lua` to specify a path explicitly. The command resolves the same repository source directory as the development launcher; old runtime copies cannot shadow edited sources. Missing and ambiguous names fail before building, with ambiguous paths listed for selection. Explicit diagnostic captures retain the exact source bytes used for that run; their hashes record provenance only. The command opens the launcher, selects its development Lua tab, and automatically runs the chosen script. The tab has a searchable list of unique scenario names without `.lua`, footer Run, Stop session and Kill all controls, activity without per-line timestamps, elapsed completion status, failure traces, and a bottom copy icon for agent handoff. The script inventory is read at launcher startup and refreshed before each run. Duplicate basenames report their conflicting paths. Console output stays in a bounded in-memory buffer rather than a separate file for each session. A fresh launcher clears old detached launch/trace logs, client-result mailboxes, and obsolete launcher console logs. Only clients launched by the current launcher are tracked; previous processes remain untracked after restart. Native registration/failure files are a temporary handoff and are deleted after their contents reach launcher memory; Send report includes the retained in-memory results.

For agents, `bin/game/darkspinner.exe --lua-headless local/two_arsenal.lua` starts only the supervisor and Lua helper, with no launcher UI. `--debug-api --lua <path>` also remains supported. Read the printed private discovery file and use its authenticated `POST /dev/scenario/v1/scripts/run` with `{"path":"local/two_arsenal.lua"}` to run another script in the same session. A running script rejects concurrent runs. Completion retains the server and clients for inspection (up to the existing 30-minute retention). Stop session calls authenticated `POST /dev/scenario/v1/scripts/stop` to cancel only the running Lua script; the supervisor, clients and server remain available, and another script can reuse them. Kill all terminates the owned clients and server. `POST /shutdown` and closing the launcher still perform full session cleanup. Compatible `scenario.StartServer({})` calls reuse that session's server. Changed server inputs require Kill all or full session shutdown first. The authenticated `POST /dev/scenario/v1/kill` force-closes session-owned clients and stops its server; it also cancels an in-progress graceful shutdown. Content snapshots use read-only SQLite online backup when the source is open or has WAL sidecars, then preserve an exact offline copy without checkpointing the source. An unrelated launcher/server is not automatically adopted or terminated.

Each script returns its entry function. The helper loads the source first, then calls that function; operations cannot run during top-level source evaluation. Server, profile and client objects retain their scope. Editor definitions are split across `definitions/` by server, profile, client, scene, UI, window, session and error scope; `scenario.lua` contains root helpers and compatibility functions.

```lua
local must = scenario.Must

return function()
    local server = must(scenario.StartServer({}))
    local profile = must(server:CreateProfile({
        name = "normal",
        hero_nouns = {1667741389, 3618328019, 749013658},
        chain_progression = 1,
    }))
    local client = must(profile:Launch({client_id = "normal", launch_mode = "normal"}))
    must(client:Login())
    must(client.Scene:Wait(scene.Arsenal))
    must(client.UI:Screenshot("arsenal"))
end
```

Fallible methods return `result, err`, or only `err` for operations such as `Close`. Use `scenario.Must(result, err)` for a required result and `scenario.Check(err)` for an error-only operation. Local aliases `must` and `check` avoid repeating the namespace. There is no manual context-label argument: structured errors already preserve operation breadcrumbs, and raised errors capture the Lua call-site traceback. `Must` raises on either a non-nil error or a nil result; false is valid. Optional results need explicit nil handling after `Check(err)`. The LuaLS nonnullable return type reflects this runtime check. The older global `run()` entry remains accepted for developer-owned scripts, but shipped scripts use returned functions and no lowercase global declarations.

`UI:Type(text)` sends one bounded batch of 1–256 printable ASCII characters through the owned window's existing handler. It does not change desktop focus or the clipboard, select a text field, or submit Enter. A processing receipt reports `processed_character_count`; it does not prove text acceptance or chat delivery. Partial processing retains its count and an error, and is never replayed. `UI:Click(x, y, "right")` opens ordinary native context menus with paired right-button input; omitted button defaults to left.

`local/mod_editor.lua` starts a fresh isolated Mod server/profile/client, opens Blitz's actual Creature Editor through `client.UI:OpenCreatureEditor(1667741389)`, captures its initial UI, clicks the native Body tab using hierarchy bounds, verifies `is_body_mode`, and saves the left body-part palette for a later review. Run `bin/game/darkspinner.exe --lua local/mod_editor.lua --lua-timeout 3m`. Both `StartServer({is_modded=true})` and `profile:Launch({is_modded=true,...})` must agree. Mod is independent of `launch_mode`; normal and detached launch paths both carry the private manifest. An optional `spore_path` selects the installed Spore source; omission uses configured/detected resources, with stock assets when no source exists. Scenario profiles do not read or reset persistent launcher Mod saves or import bindings.

`Scene:Set(scene.Editor)` deliberately remains ordinary equipment editing. `UI:OpenCreatureEditor(hero_noun)` resolves a unique owned Arsenal creature by its installed hero noun, invokes the existing Mod Creature Edit action on the game thread, waits for the reported/native Editor, and verifies explicit Mod editor ownership. Missing or ambiguous ownership fails. The starter's Body click is ordinary paired owned-window input and is followed by a separate native observation; it does not edit or save a creature.

`UI:Hierarchy()` / REST operation `client.ui_hierarchy` saves an `editor-ui-*.json` artifact beneath this client's scenario log directory and returns its path, SHA-256 and nodes. Native SPUI nodes have IDs, command IDs, one-based parent indices, flags, depth and transformed client-coordinate bounds. The returned nodes additionally include visibility/enabled status inherited from ancestors; raw artifact flags remain available for inspection. This covers native Editor UI, including Mod's native Body tab and part palette; Flash/HTML internals, display labels, clipping and occlusion are not enumerated. Nodes are snapshots, never mutable or retained native handles. Refresh after UI changes, require unique visible/enabled matches before clicking, and inspect the next snapshot/screenshot rather than treating input processing as success. Traversal is bounded to4096 nodes/depth64,128 artifacts per process and1MiB per artifact; `is_complete=false` means coverage is truncated, not that omitted controls are absent. The starter leaves the owned client in Body mode and the authenticated loopback debug endpoint available after completion; `/shutdown` gracefully closes it when finished.

`local/social_flow.lua` exercises the actual 1280×720 Social panel rather than the server party fixture: native lobby invite/accept, Add Friend, lobby chat, an abrupt detached-client disconnect in Arsenal, reconnect of the same profile, fresh invite/accept, party chat and View Profile from the friend context menu. `Party:Snapshot()` only observes membership; it performs no mutation in this starter. Disconnect must leave one host member, and rejoin must produce a newer two-member revision. Saved screenshots still require inspection for native roster, chat and profile rendering. Real runs confirmed the guest's distinct Zrin-led squad online and offline, persisted friendship after the normal profile reconnected, and native offline friend removal. Leader-loss recovery currently requires forming a new party; seamless leader migration is not established. Long display names can overlap the native Helix threat label.

A launched client defaults to a 60000-millisecond timeout. Set `timeout_ms` in `profile:Launch({...})` to choose another default, or call `scenario.Check(client:SetTimeout(45000))` later. `Login()`, `Ready()`, `Scene:Wait()`, `Scene:Set()` and `Mission:Wait()` use the current client default when their timeout is omitted; an explicit per-call timeout overrides only that call. Existing scoped objects inherit timeout changes dynamically. Timeout settings are milliseconds from 1 to 120000. `Login()` blocks for accepted live server authentication and returns `LoginObservation, err`; it does not imply native UI or world readiness.

`scenario.Time()` returns monotonic elapsed milliseconds since script execution began. Save `local started = scenario.Time()` and later compute `local elapsed = scenario.Time() - started` to measure a step. `normal:Time()` reports elapsed milliseconds since that client's launch began, including launch duration; subtract two snapshots from the same clock to measure an interval. Both return a number directly, permit fractional milliseconds, and have no error slot. Saved wall-clock timestamps remain unchanged.

Scenario launches default both `is_intro_skipped` and `is_cinematic_skipped` to true; pass false separately to retain introductory movies or in-game cinematics. The ordinary launcher defaults both to false. Live changes remain independent: `scenario.Check(client.Cinematic:SetSkipEnabled(false))` retains in-game cinematics, while `scenario.Check(client.Cinematic:SetIntroSkipEnabled(false))` retains introductory movies. Changing one switch leaves the other unchanged.

`local/two_profiles.lua` creates two isolated profiles and launches normal and detached clients. `local/seed_reset.lua` demonstrates distinct squad orders and a fresh reset before launch, verifies that reset allocated another account, and checks each accepted Arsenal login against its intended profile identity. `local/two_arsenal.lua` creates a normal seed, clones its selected squad/progression into the detached profile, and waits for Arsenal report plus owner-thread responsiveness before saving screenshots. `local/two_arsenal_parallel.lua` logs in both clients sequentially, then runs their scene waits and screenshots as named concurrent branches with a shared completion barrier.

Creating an existing profile alias, or resetting one explicitly, closes its session-owned clients and releases their launch names before creating a fresh account. Closure is attempted gracefully with bounded termination fallback for owned processes. The alias changes only after account creation and credential issuance succeed; the previous account and primary saves are unchanged. The replacement may reuse the client ID, with fresh private launch directories. Source cloning reads accounts already in the isolated server; importing a primary-save profile is unavailable.

`client:Close()` requests the ordinary window close and waits for exit; the native game may present its Quit confirmation and leave the operation waiting. `client:Terminate()` explicitly stops only that session-owned client and its detached helper, waits for exit, and returns an error-only result for `scenario.Check`. It does not confirm game save/quit dialogs. The REST equivalent already exists as `client.close` with `is_terminate=true`; `Close()` keeps its graceful behavior.

`local/repeat_mission.lua` runs two complete seeded normal/detached party mission entries on one owned server. Between passes it explicitly terminates the two owned clients, checks that both exited, resets the same profile aliases to new accounts, and launches new process identities with distinct client IDs. The second detached seed clones the newly reset normal profile. Each pass verifies the committed mission uses those intended account IDs, compares both mission identities, and saves separate per-client screenshots. A failure retains the current session for inspection.

Seed and cloned recipes keep their requested three squad heroes in order with fresh creature IDs 1, 2 and 3. The new inventory also contains any missing Blitz Alpha and Sage Alpha prerequisites so ordinary login preserves that squad instead of replacing it with the tutorial starter order.

`client.UI:InspectWindow()` makes an authenticated round trip through Fang and returns copied owned-window metadata, including its native owner thread and dimensions. `client.UI:Click(x, y)` queues a finite left click through that window's existing handler on the owner thread. Coordinates are client coordinates from `InspectWindow()`. Processing receipts prove neither enabled in-game controls nor gameplay success. The adapter sends no desktop cursor/focus commands. Requests have bounded deadlines and are never automatically replayed; timeout/disconnect may leave an unknown outcome, so inspect state before another action. The older `Window()` name remains a deprecated compatibility alias.

`client.UI:Screenshot(label)` saves the exact owned window and metadata under game logs, including for a background window. It returns `artifact, err`; unavailable capture can still return diagnostic metadata with the error. Required screenshots can use `must(client.UI:Screenshot("ready"))`. Authentication, capture success and gameplay readiness are independent observations.

`client.Diagnostics:Capture("failure")` returns `DiagnosticCapture, err` and uses the same operation as REST `client.capture` with `{client_id, label}`. It saves a manifest under the owned client's logs, a screenshot through the existing capture path, the client snapshot, allowlisted server profile/mission state, a fresh Fang window receipt, and copies of the last complete records from the client trace, server protocol trace and server log. Each log copy is capped at 512 KiB and records its sampled source size, offset, truncation and SHA256; it is a saved tail rather than a complete packet archive. Labels follow screenshot naming rules. Calls inherit the client timeout with a ten-second cap; at most 32 captures are reserved per supervisor, including partial attempts. Existing screenshot budgets also apply.

Captures are sequential observations with `is_atomic=false`; they do not pause the game or prove native world readiness. Every failed component appears in the manifest's lowercase `failures` snapshots, `is_complete` becomes false, and the call returns an error with typed `Failures`; successful components remain on disk. A stopped client can still yield retained trace tails and a partial manifest, but no newly reset alias's profile is attributed to it. Inspect the partial result before calling `check(err)` when evidence matters. Endpoint capture is observational and remains available during a running script. Pause automation until settled before inspecting the same client's native bridge to avoid competing with its one pending command. `two_clients.lua` captures both participants at final shared entry.

`client.Scene:Snapshot()` exposes accepted live authentication, current server game/party membership, retained client presence and mission lifecycle metadata through an explicit allowlist. These sources are independently sampled. `client.Scene:Wait(scene.Arsenal)` waits for authenticated matching reported presence and a pure native `scene.ready` query on the owner thread: the expected current room, loaded/enabled UI, eligible progression/mode and no active camera/movie must all match. It then rechecks report, authentication and client identity within one deadline. Explicitly unavailable eligibility probes may be retried within that deadline; this wait sends no transition or input. The result contains `client_id`, `instance_id`, `pid`, `state` and `readiness`; partial evidence may accompany an error. `client:Ready()` returns the same evidence shape with a window responsiveness probe only, without scene-specific eligibility. Neither guarantees final rendering or gameplay readiness.

Scene constants are `scene.Arsenal`, `scene.Navigation` and `scene.Editor`. Scene waits require a presence revision strictly greater than `afterRevision` (default 0). Default 0 accepts an existing retained report; capture a baseline revision first when a later changed envelope is required. Presence itself is a last client report and becomes stale after authentication ends. `Profile:WaitForReportedLocation` and compatibility location methods retain their report-only behavior; use `Client.Scene:Wait` for the additional native current-room and UI-eligibility checks.

Top-level overlays use `client.UI.Screen`, separately from the ship room. Supported constants are `screen.Profile`, `screen.Inventory`, `screen.Galaxy`, `screen.Friends`, `screen.Leaderboards`, `screen.Manual` and `screen.None`. `Set(target)` dispatches one ordinary native action and waits for observed selection; `Wait(target)` only observes, `Snapshot()` reads once, and `Close()` sets `screen.None`. All use the client timeout unless overridden. Selecting an already selected screen returns without another toggle. Close Inventory explicitly before selecting another overlay; native close gates and prompts remain intact. An unknown active modal/overlay is reported as unsupported and cannot be silently dismissed.

```lua
must(client.UI.Screen:Set(screen.Inventory))
must(client.UI.Screen:Close())
must(client.UI.Screen:Set(screen.Profile))
check(scenario.Sleep(1500)) -- Capture allowance for opening animation, not content-readiness proof.
must(client.UI:Screenshot("profile"))
must(client.UI.Screen:Close())
```

Screen operations pin the owned process/account, native UI generation and owner thread. Receipts distinguish attempted/returned native invocation from subsequent selection. Browser screens are observed through the displayed frame and selected DOM tab; the client's cached `native_screen_id` can remain `-1`, while `selection_source="dom"` identifies actual selection. `is_content_ready` remains unknown: selection does not prove network content, animations or rendering finished. `local/screen_flow.lua` adds 1500 ms before diagnostic captures, visits all six overlays, checks Inventory transition refusal, and opens Profile from Navigation before returning to Arsenal. The real flow passed in 38 seconds with eight complete capture bundles and inspected screenshots (`bin/game/logs/scenarios/screen-flow-dom-oct24/analysis.json`). REST operations are `client.screen_state`, `client.set_screen` and `client.wait_screen`; they accept `client_id`, an exact `screen` for Set/Wait, and optional `timeout_ms`. Errors retain partial observations and any attempted action; no action is replayed.

`client.Scene:Set(scene.Navigation)` first waits for current-room native eligibility, requests one ordinary ship transition on the owner thread, then waits for fresh matching reported presence and destination eligibility under one overall timeout. If the initial authenticated report already matches, it probes without sending another transition. The result contains `location`, `is_already_there`, `action` and `observation`; errors may retain partial receipts and observations. Only pure unavailable probes are retried; transition actions are never replayed automatically. Completed processing does not prove final rendering or gameplay readiness. `local/two_scenes.lua` is an authored sequential starter that moves the normal client to Navigation and the detached client to Editor, captures both, then returns them to Arsenal. The complete starter passed against real clients. Editor uses its own lifecycle readiness. From Editor, Scene:Set(scene.Arsenal) locates the ordinary Cancel button by its native identity and derives its current transformed bounds before one owned-window click; no resolution or fixed coordinates are assumed. It waits for the resulting fresh Arsenal report and native readiness, leaving save/discard prompts intact. A prompt may therefore cause the wait to time out with partial evidence. Leave Editor for Arsenal before requesting another ship room; Escape opens Options.

`client.Mission:SnapshotMission()` reads server profile and mission metadata once. Dedicated lifecycle fields distinguish `is_gameplay_available` from `is_gameplay_active`; `gameplay_unavailable_reason` explains missing observation, while `gameplay_game_id` identifies the actual binding independently of active-user `game_id`. `Mission:Wait()` requires the same owned login/game, final server dungeon setup, a deployed hero and a processed native active-world/controlled-handle observation. It returns a mission observation containing the ready snapshot in `world`. It does not establish visibility of every object or successful gameplay input. Two successful client waits alone do not prove that both joined the same mission.

`client.Party` provides explicit server fixtures through existing Blaze party handlers and normal notifications: `normal.Party:Create("local-ship-party")`, `normal.Party:Invite(detached)` and `detached.Party:Join(normal)`. `Snapshot()` reads server party identity, leader, revision and members; party ID 0 means no membership. Every operation returns `PartyObservation, err`, including mutation/projection flags and intended versus delivered notification counts. `is_native_acceptance_observed` remains false: server acceptance and sent notifications do not prove the native UI accepted or applied them. Preserve partial error receipts and inspect before retrying an attempted mutation. `local/two_party.lua` is an authored two-profile normal/detached starter that logs in, observes Arsenal, creates/invites/joins, compares both server membership snapshots and saves screenshots. Its full flow passed against real clients; it performs no mission-start operation.

An automated run of `local/two_party.lua` passed with both owned clients in the same server party. Further endpoint-driven interaction selected 1-1, started it, and pressed Continue in each client. Both `Mission:Wait()` calls observed the same game ID and committed dungeon state, and owned-window screenshots showed both heroes together in Floating Isles. This establishes shared entry, not mission completion or combat verification.

`Mission:WaitDeployment()` requires a matching active server gameplay binding at `chain-countdown-sent`, `preparing` or `dungeon`. This is a lifecycle milestone: a later stage still satisfies it, without claiming that every earlier phase was observed. It does not prove the native Continue button has rendered. Mission waits pin the first accepted login/account and nonzero game ID; a changed game fails instead of silently observing a different mission. `Mission:SnapshotSelection()` copies only allowlisted native map fields. `WaitSelection(difficulty?)` requires the Campaign difficulty screen, a settled matching carousel selection, no pending transactions, ready party members, and a visible enabled Start button. Unavailable fields remain unknown and cannot satisfy the wait. Both waits inherit the client's timeout and never send or replay input.

`Mission:Start()` waits for an eligible campaign selection, invokes the authored Play handler once, then waits for server deployment. `Mission:Continue()` waits for native Accept eligibility or the same owned session/game's committed dungeon entry. It invokes the authored AcceptMission handler at most once and waits for commitment. Party progression can enter a member before that member needs another Accept; the result then reports `is_already_entered=true`, with no action or a retained explicit no-invocation refusal receipt. Unknown native outcomes remain errors. Both methods return `MissionActionResult, err` with native action, readiness and server observation evidence, including partial results on failure. They use one overall client deadline, pin owned process/login/game identity, and never automatically replay an invocation. Native invocation acceptance proves only that the authored call returned successfully; the server wait checks the resulting operation. `SnapshotDeployment()` exposes the copied native UI fields; `WaitDeploymentReady()` makes the pure eligibility check without invoking Accept.

For a party, invoke both blocking Continue operations in `scenario.Parallel`: the server may wait for every member to accept before anyone reaches the dungeon. Independent branches can progress while the shared barrier waits. Start is called by the leader for the selected party mission.

`Mission:Select(1)` opens Campaign when needed and moves the native difficulty carousel through its ordinary Previous/Next handlers. It waits for the exact resulting selection after each distinct step, pins the client/login identity outside any active game, and returns `MissionSelectResult, err` with accumulated action receipts and the last native observation. It supports Infection mode (native mode 1), difficulties 1–24; other modes are not switched automatically. An already-selected difficulty returns without another action. Native guard refusal, timeout or unknown outcome stops the sequence; an attempted step is never replayed.

`local/two_clients.lua` combines the full workflow in one run: create and reset the normal profile, clone its selected squad into the detached profile, verify both Arsenal account identities, visit Navigation and Editor, return both clients to Arsenal, form one two-member party, and enter mission 1-1 together. It also checks deployment waits after dungeon commitment, compares game/account identities, and saves seeded, scene and final dungeon screenshots. Both clients remain available for endpoint inspection after the script returns. Start it with `darkspinner.exe --lua local/two_clients.lua` from a scenario build.

`local/two_mission.lua` creates two seeded clients, joins one party, selects 1-1 with `Mission:Select(1)`, starts it and continues both members into the same mission. Selection, Start and Continue use scoped operations with native guards and observed outcomes; the mission starter has no coordinate clicks or resolution assumption. `scenario.Check(scenario.Sleep(ms))` provides a bounded cancellable delay, including inside Parallel branches, and makes no readiness claim. The starter retains a short delay only for the final capture fade. Scene return from Editor also resolves the live Cancel control instead of using fixed coordinates.

`scenario.Parallel({normal = function() ... end, detached = function() ... end})` runs at most eight named branches on the supervised scheduler and waits for all of them at a shared barrier. Pass its error-only result to `scenario.Check`. A barrier failure retains every failed branch in `err.Failures`. Branches can perform independent client operations and observation waits; nested Parallel and server/profile/client lifecycle mutations are rejected. Parallel does not expose a second Lua VM or arbitrary user coroutine creation.

`local/cinematic_toggle.lua` demonstrates a client timeout override, independent live cinematic switches, and screenshot labels containing script/client elapsed milliseconds. Runtime switch receipts confirm configuration only; they do not claim a movie actually skipped. Intro movies and in-game cinematics have separate launcher options, both off by default for ordinary launches and on by default for scenario launches. The implementation answers Escape only at validated native cinematic decision points, preserving the original completion path; it no longer runs the old movie-stop worker or camera/menu acceleration hooks. The user confirmed the live movie-skip behavior works.

Client defaults also bound UI operations and cinematic configuration requests. Native bridge requests and screenshots retain their shorter operation-specific caps, so increasing the client default does not extend those caps. The REST operation envelope accepts an optional `timeout_ms` (up to 120000) independently of each wait's payload deadline.

The helper exposes base/string/table/math libraries, without file/module/dynamic loaders, operating-system or debug libraries. Its default execution limit is 180 seconds with a five-second outer watchdog allowance and a 256 MiB helper-only Windows job cap. `--lua-timeout 20m` explicitly extends a script's budget; accepted limits are 1 second through 30 minutes. Client operation deadlines remain independent. Script return or failure leaves a 30-minute authenticated inspection session; owned resources remain until shutdown or expiry. Scripts are never executed merely because they are listed. Editing the active on-disk source takes effect on the next run without rebuilding the launcher.

Profiles, owned client instances, launch mode and party role are distinct identities. Future remote participants are represented by definition types only; remote launch/control is unavailable and no remote debug listener is enabled. Native party acceptance and shared mission entry remain separate observations from the server party fixture. `SpawnAsync` returns a correlated pending receipt; `SnapshotSpawn` observes actual server admission/publication without replay.

`World:Snapshot()` samples bounded server world observations once without waiting. `World:SnapshotLiving()` samples once and fails if the world is unavailable or terminal, or its deployed hero is missing, defeated or out of health; failures retain the partial snapshot. `World:Ready(timeout_ms?)` waits for committed dungeon setup, a deployed server hero and a processed native active-world/controlled-handle observation, returning a snapshot with `native_readiness`. It pins the process, accepted account/session and admitted game, stops on ownership changes, and retries only explicit query unavailability. This establishes neither visibility of every object nor successful input. `Mission:Wait()` now requires that same readiness and retains it in `observation.world`; an arbitrary arrival sleep is unnecessary. `Mission:Enter(difficulty, timeout_ms?)` composes Select, Start, Continue and readiness under one total timeout. It returns a snapshot, not the `client.World` controller; discard it when only entering, or name it `worldSS` when inspecting it. Entry starts from the authenticated navigation flow outside an active game, stops on the first failed step, preserves its partial receipt and never replays attempted actions. `SpawnControlledNPC()` still waits independently for its newly requested NPC's server publication. Server publication does not prove native visibility. `is_zone_terminal` includes retirement/discard; only `is_victory_available` plus `is_victory_committed` establishes the current member's committed victory. Native handles from `SnapshotNative()` are separate from server object IDs.

`World:Click(point)` projects a finite world coordinate and supplies one press/release through the ordinary native ray and gameplay input polls. It preserves native movement/attack/interaction decisions. Its receipt proves processing only: inspect position, damage, death or route traversal separately. Unknown outcomes stop the action sequence and must not be replayed. Guard refusal can occur during a modal dialog, physical input, scene changes or absent gameplay state.

`World:Hold(point, duration_ms)` sustains the same ordinary held input for 1–1200 milliseconds and returns only after the matching release poll. The native deadline remains two seconds, or the shorter client deadline. Cancellation withdraws the synthetic input; a consumed press without a witnessed release reports an unknown outcome. `Click` remains a short tap.

`World:Path(start, goal)` performs a read-only bounded search on the installed navigation mesh with the owned hero's footprint and scene obstacles. At most 128 points are retained. `is_complete` reaches the projected mesh goal, which can differ from the authored target; incomplete or truncated results do not supply a usable route. No supported route within the search budget is not a proof that no route exists, and a supported route never proves native movement acceptance.

World-point projection chooses a screen ray, so native terrain picking can produce an endpoint with different X, Y and Z. The solo starter plans through installed mesh waypoints from its freshly observed native position, filters enemy candidates to roughly the current elevation, and skips candidates without a complete supported route. It checks that the projected endpoint remains within three world units of the intended target, including height, rather than assuming a complete path reaches the authored target. Ground navigation follows the next mesh segment in steps of at most six world units even when a distant waypoint projects on screen, because a nearer bridge edge can intercept that ray; direct visible actor targeting within twelve units remains separate. Each native movement step requires horizontal progress before replanning; a successful native ground query supplies its actual chosen ground point.
